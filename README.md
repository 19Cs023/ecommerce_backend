# E-Commerce Backend (FastAPI)

A production-shaped e-commerce API, built to be **read**, not just run.
Every file has inline comments explaining *why* a decision was made, not
just what the code does — the goal is that you can lift individual
patterns out of this codebase and reuse them elsewhere.

> ⚠️ **I could not execute this code before handing it to you.** The
> sandbox this was built in has no network access, so `pip install`
> could not run and the test suite was never actually executed — every
> file was checked for syntax errors (`py_compile`) and the import graph
> was traced by hand for circularity, but that is not the same guarantee
> as a green test run. **Your first step should be running the test
> suite yourself** (instructions below) before trusting this in any real
> project. If something's broken, it's most likely a small, fixable
> thing — but don't skip this step.

## 1. Quickstart

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

pip install -r requirements.txt

cp .env.example .env
# Open .env and set SECRET_KEY to a real random value:
python -c "import secrets; print(secrets.token_hex(32))"

# Run the test suite FIRST — this is the real verification step I couldn't do.
pytest -v

# If tests pass, run the API:
uvicorn app.main:app --reload
```

Then open **http://localhost:8000/docs** for interactive Swagger docs
(auto-generated by FastAPI from the Pydantic schemas).

Default DB is SQLite (`ecommerce.db`, created automatically on startup) —
zero setup needed to try it. Switch `DATABASE_URL` in `.env` to a Postgres
URL for anything beyond local exploration.

## 2. The layered architecture, and why it's shaped this way

```
Request
  → app/api/v1/endpoints/*.py   (HTTP concerns: status codes, request/response shape)
  → app/services/*.py           (business logic that spans multiple models)
  → app/crud/*.py                (one repository per model: raw DB queries)
  → app/models/*.py              (SQLAlchemy ORM — what's actually in the DB)
  → app/schemas/*.py              (Pydantic — what goes over the wire)
```

**The rule this enforces:** a route handler never writes raw SQLAlchemy
queries, and a CRUD function never knows anything about HTTP. This means:

- You can unit-test `services/order_service.checkout()` without spinning
  up FastAPI at all — it's just a function that takes a `Session`.
- You can swap out FastAPI for another framework and only rewrite the
  `api/` layer.
- You can swap out SQLAlchemy for a different ORM and only rewrite the
  `crud/` layer.
- Business rules ("checkout must fail atomically if any item is out of
  stock") live in exactly one place, callable from a route, a CLI script,
  or a background job equally.

This is the single biggest idea to take from this project into any other
backend: **draw boundaries around what changes for different reasons.**
HTTP status codes change for HTTP reasons. SQL queries change for
database reasons. Business rules change for business reasons. Mixing
them means every change risks breaking something unrelated.

## 3. Where to start reading

Read in this order — it mirrors how a request actually flows, and each
file's docstring explains the *why* behind that layer:

1. `app/models/` — start with `user.py`, then `product.py`, then
   `order.py`. The `order.py` docstring explains the most important
   single design decision in this codebase: **price/name snapshotting**.
2. `app/schemas/` — compare `ProductCreate` vs `ProductRead` vs
   `ProductUpdate` in `product.py`. Notice they're deliberately different
   shapes, not one class reused three ways.
3. `app/crud/base.py` — the generic repository pattern. Then
   `crud/product.py`'s `decrement_stock()` — read the comment on
   `with_for_update()` closely; it's the difference between a toy app and
   one that doesn't oversell inventory under concurrent checkouts.
4. `app/services/order_service.py` — the checkout transaction. This is
   where the "all or nothing" guarantee across Cart/Product/Order lives.
5. `app/api/deps.py` — the auth dependency chain
   (`get_current_user` → `get_current_active_user` → `get_current_admin_user`).
6. `app/api/v1/endpoints/orders.py` — see how thin the route handler is
   once the service layer exists; it only translates exceptions to HTTP
   status codes.

## 4. Patterns worth reusing elsewhere

| Pattern | Where | What it solves |
|---|---|---|
| Settings object (pydantic-settings) | `core/config.py` | Typos in env var names caught at startup, not at 3am in prod |
| Money as integer cents | `models/product.py` | Floats can't represent decimals exactly; rounding errors compound |
| Snapshot-at-time-of-event | `models/order.py` | Historical records (invoices) shouldn't change when the live data does |
| Repository / CRUD base class | `crud/base.py` | One implementation of get/create/update/delete for every model |
| Service layer for cross-model logic | `services/order_service.py` | Business rules callable from anywhere, testable without a web framework |
| Dependency chaining for auth | `api/deps.py` | Compose small checks (`is authenticated` → `is active` → `is admin`) instead of one monolithic function |
| Separate schema per operation | `schemas/*.py` | Structurally impossible to leak a password hash if `UserRead` never declares that field |
| Row locking for inventory | `crud/product.py` `decrement_stock` | Prevents overselling under concurrent checkout requests |
| Ownership checks return 404, not 403 | `api/v1/endpoints/orders.py` | Doesn't confirm to an attacker that an order ID *exists* but belongs to someone else |
| Same error for "no such user" and "wrong password" | `api/v1/endpoints/auth.py` | Prevents account enumeration via the login endpoint |
| Envelope object for list responses | `schemas/product.py` `ProductListResponse` | Room to add pagination metadata later without a breaking change |

## 5. Database migrations (Alembic)

This project ships a migration setup instead of relying on
`Base.metadata.create_all()` for anything beyond local dev (see the
comment on `on_startup()` in `main.py` for why `create_all` is
dev-only — it never alters existing tables).

```bash
# Apply all migrations (creates the schema from scratch)
alembic upgrade head

# After changing a model, generate a new migration:
alembic revision --autogenerate -m "add discount_code to orders"
# ALWAYS read the generated file before running it — autogenerate
# sees a column rename as "drop + add" and will happily delete data.

alembic upgrade head
```

The included `alembic/versions/0001_initial_schema.py` was hand-written
(not autogenerated) since generating it requires a live DB connection —
read it as a plain example of what a migration file contains.

## 6. Running the tests

```bash
pytest -v
```

Tests use an in-memory SQLite DB, recreated fresh per test function (see
`tests/conftest.py` for why `StaticPool` is required for this to work
correctly). No external DB needed to run them.

What's covered:
- `tests/test_auth.py` — registration, login, wrong-password rejection,
  duplicate-email rejection, and the (important) assertion that a
  password hash never appears in an API response.
- `tests/test_cart_and_checkout.py` — the full add-to-cart → checkout
  flow, an out-of-stock checkout failure, an empty-cart checkout
  rejection, and the ownership check that stops one user from viewing
  another's order.

**These are the tests I could not run for you.** If any fail, they're
almost certainly catching a real issue — start there before assuming the
test itself is wrong.

## 7. What's intentionally simplified (read before calling this "done")

This is a teaching artifact, not a finished commercial product. Specific
things a real production system would add:

- **Payments**: `checkout()` marks orders `PAID` immediately with no
  actual payment gateway integration (Stripe, etc.). A real system sets
  `PENDING`, redirects to a payment provider, and flips to `PAID` only
  from a verified webhook.
- **Hard delete on products**: `DELETE /products/{id}` really deletes
  the row. The comment in `products.py` explains why a soft delete
  (`is_active = False`) is the safer real choice — it avoids breaking the
  FK on historical `OrderItem` rows.
- **No rate limiting** on `/auth/login` — a real deployment needs this
  to slow down brute-force password guessing.
- **No email verification** on registration.
- **No refresh-token revocation list** — a stolen refresh token is valid
  until it naturally expires; there's no "log out everywhere" mechanism.
- **CORS origins** are read from `.env` but you still need to set them
  correctly for your actual frontend's domain before deploying.

None of these are bugs — they're scope boundaries, called out so you
don't mistake "not built" for "built wrong."
